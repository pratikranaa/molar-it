About Molar · the evidence-first thesis

Evidence should outlive the run.

A browser action is temporary. The evidence behind a release decision should remain legible to the person reviewing it and the coding agent acting next.

Why now

More generated code creates more change to verify.

Change volume Coding agents can create and revise software faster than a human team can manually exercise every important path.

Browser reality Compilation and isolated tests cannot prove that identity, permissions, payments, messaging, storage, and asynchronous state work together.

Durable context A useful run leaves a receipt that explains what was attempted, what was observed, and why the outcome was adjudicated that way.

What counts as evidence

Success is an observed outcome with a visible boundary.

An evidence-first run People + agents

Outcome

What the user could do

The browser state, page behavior, and assertion that made the goal pass or fail.

Cause

What shaped the result

Actions, logs, network context, and configured external state that explain what happened.

Boundary

What remains uncertain

Uncovered branches, missing integrations, skipped work, and evidence the system could not obtain.

How we think

Uncertainty belongs in the product, not in the fine print.

Truth before theatre Molar should distinguish current, limited, proposed, and deployment-dependent behavior instead of flattening it into one promise.

Controlled consequence Verification should use explicit safety budgets and controlled state when configured, especially around payments, credentials, messages, and destructive actions.

No universal sensor Molar does not promise to observe every modality or infer state it cannot access. The receipt should expose those limits.

Compounding evidence A verified flow can inform debugging, release gates, monitoring, and reusable automation without pretending the original evidence is timeless.
