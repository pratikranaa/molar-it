Add a check to each
stage of your release.

Guard becomes useful when its target, credentials, scenario, and merge policy are explicit. Configure them once, then inspect the result for each pull request and deployment.

01

Prepare

Install and authenticate the CLI. Connect the repository and preview environment. Give the scenario a dedicated test account and only the service endpoints it needs.

02

Gate

Run the configured scenario in CI and mark the chosen GitHub job as required in repository settings. Guard reports the result; your branch protection policy decides whether a merge is allowed.

03

Observe

After deployment, schedule an authorized login, checkout, or account check against the selected URL. Use marked identities and keep side effects inside the probe-owned data.

04

Investigate

Open the failed assertion, browser steps, screenshots, and available Trace reference. Mender can prepare a repair preview for review; a human still decides what enters the repository.

Questions,
answered.

Have a specific workflow in mind?
Let’s talk it through

What does Guard run?

Guard runs configured scenarios in CI, after deployment, or on a schedule. A scenario can follow a browser journey and check the resulting application state; supported Clones can provide isolated payment, email, identity, SMS, or storage behavior where the workflow needs it.

How does Guard choose tests?

Your repository policy names the scenarios and release moments to run. A diff or changed area can be one input to that policy. Confirm the configured scenario set before making a job required.

What do I need before adding the CI job?

Install and authenticate the CLI, connect the repository and target environment, define the scenario and its assertions, and prepare dedicated test credentials or Clones. Keep secrets in your CI secret store and make the selected GitHub job required in repository settings.

Can Guard check a preview or production URL?

Yes, for an authorized workflow. Use the preview URL for a release check and a scheduled, permission-scoped target for production monitoring. Production probes should use marked identities and side effects confined to probe-owned data.

What does a failed run show?

The result keeps the scenario and run identity with the failed assertion and available browser steps, screenshots, artifacts, and Trace reference. Check whether the failure is an application assertion, missing access, or environment setup issue before rerunning.

Does Guard replace Playwright?

No. Guard can complement an existing Playwright suite. Evaluate the configured scenario, environment setup, evidence, and maintenance work on a flow that matters to your team.

Will Mender merge or deploy a fix?

No. Mender is a preview workflow that prepares a proposed repair for review. A human reviews the diff and repository policy remains in control of approval, merge, and deployment.
