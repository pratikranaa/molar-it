Connect your app to the test service

Start the required clone and configure your development or CI environment to use its endpoint. Keep production credentials out of that environment. Your app sends its usual requests to the clone; your test can inspect the records it creates.

  • Choose the APIs your app calls
  • Configure the test endpoint and credentials
  • Check the resulting payment, message, or file record

Reproduce a decline, delay, or expiry

Set up the supported failure state before the browser test. A declined payment should show a retry; an expired verification code should leave the account signed out. A virtual clock lets you exercise time-based behavior without waiting.

  • Payment declines and retries
  • Subscription renewals
  • Message delivery and code expiry

Reset the data before the next test

Save a JSON snapshot of the services before a test, then restore it for the next attempt. Deterministic IDs help you recognize the same records across runs. A previous successful purchase should not make a broken checkout pass.

  • Snapshot and restore
  • Separate state for each run
  • Repeatable local and CI tests

Let’s talk it through

What are the five core Clones?

The catalog includes Stripe, Twilio, Email, Auth, and S3 service clones for payment, messaging, email, identity, and object-storage paths.

Can Clones charge a real card or send a real message?

No. Clone traffic stays in isolated test services, and the TypeScript SDK blocks known destructive calls to live vendors.

Which Stripe behavior is covered?

The current Stripe clone covers payment methods, declines, 3DS-required states, PaymentIntents, subscriptions, invoices, checkout sessions, disputes, refunds, and related webhooks.

Can I test time-based behavior?

Yes. The virtual clock supports flows such as trial expiry, delayed delivery, renewals, and expired verification codes where the relevant clone implements that behavior.

How do snapshots help a test?

Take a JSON snapshot before the journey, mutate the service state during the run, then restore it before another attempt so IDs and starting conditions are deterministic.

How much vendor coverage do I get?

Each clone covers specific APIs and state transitions. Check the catalog or contact us before relying on a provider behavior outside the documented paths.
